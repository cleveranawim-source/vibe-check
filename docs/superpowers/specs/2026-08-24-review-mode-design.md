# 바이브체크 심사 모드(Review Mode) 설계

2026-08-24 · 브레인스토밍 합의 결과 (Yeol × Claude)

## 1. 배경과 목적

바이브체크는 현재 교사 자가점검 도구다(보안 스캔 + 개인정보·AI윤리·운영 체크리스트).
최종 목표는 **교육청 공인인증의 심사 인프라**: 전국 교사가 바이브 코딩으로 만든 앱을
법적·교육적·보안적 기준으로 심사하고, 통과한 앱에 기관이 인증을 부여하는 구조.

핵심 전제 전환: 자가점검은 "정직한 답변"을 전제하지만 심사는 "통과하고 싶은 사람"을
전제한다. 따라서 **자기신고(체크리스트 응답)가 아니라 증거(자동 스캔, AI 코드 분석,
심사자 확인) 중심**으로 재편한다.

## 2. 합의된 결정사항

| 쟁점 | 결정 |
|------|------|
| 판정 구조 | **자동 증거 수집 + 인간 심사단 최종 판정** (완전 자동화 배제 — 사람이 최종 확인) |
| 자기신고 | 배제. 개인정보 수합 구조조차 AI가 코드에서 직접 분석 |
| 인프라 | 경량(심사자 모드) + 자동 분석 파이프라인. 제출함·계정·인증 대장은 파일럿 후 |
| 공개성 | 심사 모드는 공개 — 교사가 제출 전 **모의심사** 가능. 공인 권위는 도구가 아니라 심사단 확인 기록·인증 대장에서 나옴 |
| 카테고리 | 교사 업무 지형 기준 4트랙: 교무·행정 자동화 / 교과 수업 도구 / 학습 콘텐츠·활동 / 학급 운영·소통. **AI가 코드에서 추론, 심사자가 확정.** 학습 콘텐츠는 성취기준 태깅(1차: 교과·학년군 선택+코드 직접 입력) |
| AI 비용 | 심사자의 API 키. 앱 1건 전체 분석 ≈ 몇백 원 (Opus 5 기준) |

## 3. 심사 흐름

```
GitHub 주소 입력
  → ① 규칙 스캔 (조작 불가능한 팩트: 30+ 규칙, 프로젝트 규칙 포함)
  → ② AI 카테고리 추론 (근거 제시 → 심사자 확정)
  → ③ 카테고리 트랙의 루브릭에 대해 AI가 항목별 판정 초안 작성
  → ④ 사람 전용 항목(교육적 적절성, 성취기준 부합 등)은 심사자 수동 입력
  → ⑤ 심사 보고서 생성 (인쇄/PDF)
```

## 4. AI 판정의 신뢰성 원칙 (설계의 심장)

- AI 출력은 "판정"이 아니라 **"판정 초안 + 근거 인용"**.
- 항목별 판정값: `충족 / 미충족 / 판단불가(사람 확인 필요) / 해당없음`.
- **모든 판정에 근거 코드 위치(파일·줄·인용) 강제.** 근거를 못 대면 판단불가로 강등.
- 확신이 없으면 미충족이 아니라 판단불가로 내리도록 프롬프트 설계 (과잉 판정 방지).
- 심사자는 항목마다 근거를 확인하고 **승인 또는 번복**. 번복은 사유와 함께 기록.
- AI는 심사단을 대체하지 않는다 — 심사단의 눈을 코드 속으로 데려간다.

## 5. 루브릭 구조

- 두 층: **필수 요건**(하나라도 미충족 = 불합격 후보) + **점수 요건**(카테고리별 가중).
- 필수 요건 예: 주민번호 수집, 비밀키 노출, 열린 DB 쓰기 규칙, 개인정보 수집 시
  만 14세 미만 동의 부재, 상담형의 위기대응 부재, (교무 자동화) 학생 실데이터의
  외부 AI 전송·공개 저장소 노출.
- 기존 체크리스트 문항(개인정보 12 + AI윤리 12 + 운영 5)을 루브릭 항목으로 승격하되,
  각 항목에 `aiVerifiable`(코드로 검증 가능 여부)을 표시. 불가 항목은 심사자 수동란.
- **루브릭에 버전 번호**(v1.0부터). 보고서에 "루브릭 vX.Y로 심사됨" 기록 — 재현성.

## 6. 변조 방지

- 심사 시점의 **커밋 해시(branch head SHA)를 보고서에 고정 기록**:
  "이 심사는 커밋 `abc1234`에 대한 것."
- 인증 후 코드 수정 시 재심사 원칙을 규정에 명시(운영 규정 문서, 도구 밖).

## 7. 컴포넌트 설계 (구현 관점)

| 컴포넌트 | 내용 |
|----------|------|
| 심사 모드 진입 | 기존 앱 안의 별도 모드(헤더 또는 홈에서 진입). 일반 모드와 코드 공유 |
| 카테고리 추론 | AI 호출 1회, JSON 스키마 강제: `{category, confidence, evidence[]}` |
| 루브릭 데이터 | `src/data/rubric.js` — `{id, version, tracks[], type: required|scored, weight, aiVerifiable, question, evidenceHint}` |
| AI 항목 판정 | 항목 묶음 단위 AI 호출, JSON: `{itemId, verdict, evidence: [{file, line, quote}], reasoning}` — 파싱 실패 시 재시도 |
| 심사자 오버라이드 | 항목별 `{aiVerdict, humanVerdict, note}` — 번복 기록 보존 |
| 커밋 해시 | GitHub API(이미 사용 중)에서 head SHA 획득, 보고서에 표기 |
| 심사 보고서 | 커밋 해시·루브릭 버전·판정표(근거 인용)·종합 의견·심사자 확인란. 인쇄/PDF |
| 성취기준 태깅 | 학습 콘텐츠 트랙: 교과·학년군 선택 + 성취기준 코드/문장 직접 입력 (전체 DB는 NCIC 공식 데이터 확보 후) |

## 8. 비범위 (이번 단계에서 만들지 않는 것)

- 제출함, 심사단 계정·로그인, 인증 대장(공개 저장소), 인증서 진위 확인 페이지
- 성취기준 전체 선택기(공식 데이터 필요)
- 서버 측 AI 분석 (심사자 키로 브라우저에서 실행)

## 9. 파일럿 계획

심사 모드 완성 후, Yeol의 기존 앱 5~10건(감정일기, 마음 점프, 감정 내려놓기 등)을
실제 심사하여 루브릭 v1.0의 판정 정확도·판단불가 비율·소요 시간을 측정하고
루브릭을 개정한다. 이 데이터가 교육청 제안의 근거 자료가 된다.
