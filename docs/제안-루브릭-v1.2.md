# 바이브체크 루브릭 v1.1 추가 항목 제안

> 2026-08-24 · 호성T 수학 플랫폼(hosungt-math-platform-next)의 실측 사례를 근거로 작성.
> 대상: 바이브체크 — 교사 제작 앱 심사·검수 시스템 (루브릭 v1.0 기준).
> 배점(3·2)은 기존 루브릭 분포에 맞춘 제안값 — 60점 요건과 합산해 조정 필요.

## 요약 — v1.0이 비어 있는 세 영역

v1.0은 **수집 시점**(무엇을 수집하나, 고지했나)과 **저장소 보안**(키 노출, 쓰기 공개)은 잘 덮고 있음. 참조 플랫폼이 실전에서 크게 데었던 세 영역이 빠져 있음:

1. **클라이언트 위조** — 점수·기록은 클라이언트가 보낸 값 그대로면 전부 조작 가능 (spec 28 실측)
2. **표시 단계 프라이버시** — 수집은 최소여도 랭킹·프로젝터 화면에서 실명이 샘 (spec 46 실측)
3. **파기의 실행 가능성** — "파기 계획"이 아니라 삭제 버튼·절차가 실제로 존재하고 완전한가 (spec 31, cascade 누락 사고 2회 실측)

## 1. 필수 추가 후보 (3건)

|---|---|---|---|---|
| 필수 | 점수·완료·보상 등 경쟁/보상에 쓰이는 값을 클라이언트가 임의로 쓸 수 없다 (경쟁·보상 기능이 없으면 해당없음) | 클라이언트가 계산한 점수를 그대로 DB에 write하면 **미충족**. 서버(함수·RPC) 계산이거나 보안 규칙이 값을 검증하면 충족 | 부분 — write 호출에 score·point·clear류 필드 포함 여부 grep, 최종 판정은 규칙 파일 필요 | spec 28: 위조 경로 실측 후 "완성·점수·락아웃 게이트는 서버가 이미 기록한 데이터에서만 파생"을 보안 invariant로 명문화 |
| 필수 | 학생 A가 학생 B의 기록을 덮어쓰기·삭제·사칭할 수 없다 | 문서 경로의 학생 ID를 클라이언트가 임의 지정할 수 있고 규칙에 본인 제한(auth.uid 매칭 등)이 없으면 **미충족** | 부분 — 경로 구성 코드는 grep 가능, 차단 여부는 규칙 파일 필요 | spec 36: "담당 관계 확인만으로는 우회된다" 실측 → 모든 staff 기능에 서버측 role 선체크 강제. v1.0의 "A를 B가 **볼 수** 없다"(읽기)의 **쓰기** 짝 |
| 필수 | 학생의 자유 입력이 LLM 등 외부 API로 전송된다면 그 사실을 고지하고 "개인정보를 입력하지 말라"는 안내가 있다 (그런 기능이 없으면 해당없음) | 학생 입력을 외부 AI API로 보내는 호출이 있는데 고지·안내가 둘 다 없으면 **미충족** | 부분 — api.openai.com·generativelanguage 등 엔드포인트 grep은 자동, 고지 문구는 육안 | spec 51: 처리위탁+국외이전이 동시에 걸리는 지점. v1.0의 AI 항목 2개("AI가 만든 것 표시"·"틀릴 수 있음")는 **출력**만 봄 — 위험은 **입력** 쪽 |

## 2. 점수 추가 후보 (7건)

| 구분 | 항목 (제안 문안) | 판정 기준 | 자동 스캔 | 근거 (참조 플랫폼 실측) |
|---|---|---|---|---|
| 점수 (3) | 평가·경쟁 목적 문항의 정답·채점 기준이 클라이언트(번들·정적 JSON·네트워크 응답)에 내려오지 않는다 (정답 공개가 무해한 연습용 설계면 해당없음) | 정적 JSON·번들에서 정답 필드가 보이면 **미충족**. 채점 키워드·힌트 분기 조건도 정답과 등가로 취급 | **가능** — 정답 필드명·canary 문자열을 빌드 산출물에서 스캔 | `scripts/check-worksheet-bundle.mjs`(정답 문자열 canary → 빌드 산출물 0건)를 배포 게이트로 운영. spec 47: import 한 줄로 정답 계산기 모듈이 학생 청크에 실린 사고 실측 |
| 점수 (3) | 다른 학생·외부인에게 보이는 화면(랭킹·결과 공유·프로젝터 투사)에 실명·학번이 노출되지 않는다 | 공개 화면에 실명 표시, 또는 "닉네임에 실명을 쓰라"는 안내가 있으면 **미충족** | 육안 (렌더링 코드 필요) | spec 46: 정당 수집한 실명도 랭킹 공개 화면 때문에 닉네임 전면 전환(`coalesce(nickname,'익명')`·실명 fallback 금지)을 별도 spec으로 치름. 교실 특유 노출면 = 프로젝터 |
| 점수 (3) | 특정 학생 1명의 데이터를 지울 수단이 있고, 삭제 시 진행도·기록·랭킹 등 파생 데이터도 함께 지워진다 | 삭제 기능·문서화된 절차가 전혀 없으면 **미충족**. 삭제해도 파생 컬렉션이 남으면 감점 | 육안 + 파생 컬렉션 대조표 | spec 31: 강퇴=hard delete를 파기 경로로 재사용. 간접 참조(2차 FK) 누락으로 삭제 실패 사고 2회(마이그 0086·0108) → "신규 테이블마다 user 삭제 시 이 행은?" 규칙화. PIPA 파기 요구권의 실행 수단 |
| 점수 (2) | 교사 전용 화면·기능이 URL 추측이나 버튼 숨김만으로 보호되지 않는다 | `#teacher`류 URL만으로 전체 명단·제어 기능이 열리면 **미충족**. 별도 코드/비밀번호가 있어도 검증이 클라이언트 if문뿐이면 감점 | 부분 — 해시·쿼리 분기 grep 가능, 검증 위치는 육안 | spec 36 staff RPC 패턴: target role 선체크를 서버에서 |

## 3. 심사 절차 개선 (루브릭 항목이 아닌 시스템 쪽, 2건)

| 개선 | 내용 | 기대 효과 |
|---|---|---|
| 제출 완결성 사전 게이트 | 심사 시작 전 ① 빌드 가능한 전체 소스 ② 보안 규칙 파일(firestore.rules 등) ③ 배포물과 소스 일치(커밋 SHA) 확인 — 미비 시 심사 대신 반려 | 2026-08-24 심사 보고서(Community_builders)의 판단불가 16건 사유가 거의 전부 "컴포넌트·규칙 파일 미제출". 항목 추가보다 판단불가 감소 효과가 큼 |
| 비밀키 스캔을 git 히스토리까지 확장 | 현재 커밋만이 아니라 전체 히스토리에서 키 패턴 스캔. 발견 시 "삭제 커밋"이 아니라 **재발급(rotate)** 을 권고 문구로 | 히스토리의 키는 지워도 이미 유출된 것. 참조 플랫폼 규칙 "1회성 작업에 쓴 키는 사용 후 rotate"와 동일 원리 |

## 4. 우선순위

사고로 직결되는 경로 순:

1. **점수 위조 불가** (필수 1행) — 경쟁·보상 있는 앱의 기본 전제
2. **타인 기록 쓰기·사칭 불가** (필수 2행) — 읽기 항목의 빠진 반쪽
3. **정답 비노출** (점수 3점 1행) — 퀴즈형 바이브코딩 앱에서 가장 흔한 구멍 (F12로 정답 열람)
4. **학생 단위 삭제 수단** (점수 3점 3행) — 보호자 파기 요구 시 실행 불가능한 앱이 대부분
